# Technical Decisions — Guardian Order Service

This document records the key architectural and technical decisions made during the development of the order-service.

## UUID instead of Long as ID
Long is sequential and generated by the database. With multiple databases in microservices, product id 1 and order id 1 collide when data crosses services. UUID is generated independently, never collides.

## Flyway instead of Hibernate ddl-auto
`ddl-auto=create` can drop tables in production and lose data. Flyway versions each change as a numbered SQL file that runs once — traceable and safe.

## Rich Domain Model
Business rules stay in the entity. `Order.updateStatus()` prevents cancelled orders from being updated regardless of who calls it. Status transitions are validated inside the entity.

## OrderStatus as Enum with Transition Validation

Order status was initially a raw `String`, allowing any value to be persisted and no control over valid state changes. Replaced with an `OrderStatus` enum (CREATED, AWAITING_PAYMENT, APPROVED, REJECTED, CANCELED) to guarantee only valid values exist.

Transition rules are enforced by a separate `OrderStatusTransitionValidator` class, not inside the enum itself. This keeps the enum as a pure set of values (what an order can be) while transition logic (what changes are allowed) stays isolated as a business rule that can evolve independently — e.g. APPROVED and REJECTED are terminal states, so a delayed or out-of-order event cannot silently overwrite a final status.

This decision was made in preparation for Phase 2 (Kafka), where payment-service will publish events that trigger order status changes asynchronously — making strict transition validation essential to avoid inconsistent state from out-of-order events.

## Database per Service
Each microservice owns its own database. If one database goes down, only that service is affected. catalog-service uses port 5433, order-service uses port 5434.

## RestTemplate for inter-service communication
Synchronous HTTP communication with catalog-service to validate product existence before creating an order. Simple and sufficient for Phase 1. Kafka will replace this in Phase 2 for async communication.

## ResourceNotFoundException returns 404
Custom exception that extends RuntimeException. Used when a resource does not exist — returns 404 Not Found instead of the generic 400 Bad Request.

## Environment Variables for credentials and URLs
Database credentials and catalog-service URL configured via environment variables with default values for local development.

## Separate Spring profiles (dev/test)
`dev` profile connects to PostgreSQL. `test` profile uses H2 in-memory database for unit tests — no external dependencies needed.

## Pagination on GET /orders
Returns orders in pages instead of all at once. Prevents performance issues with large datasets.

## OrderStatus Persisted as STRING, not ORDINAL

By default, JPA/Hibernate persists enums as their ordinal position (an integer) in the database. This is fragile: reordering or inserting a new value in the middle of the enum silently changes the meaning of already-stored data, with no error raised.

Added `@Enumerated(EnumType.STRING)` to the `status` field so the enum's name (e.g. "APPROVED") is stored instead of its position. This makes the column resilient to future changes in the enum's declaration order.
